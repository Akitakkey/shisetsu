# schedule-app（訪問スケジュール GASアプリ）

Google Apps Script (GAS) の Web アプリ。薬剤師の訪問予定をGoogleカレンダー1本で
管理する、日表示のスケジュールボード。リポジトリ直下の「施設訪問記録」PWA
（`../index.html`）とは**別の独立したアプリ**で、コードもデータも共有していない。
ユーザーが会話中にコードをアップロードしてくれたものをこの場所に取り込んで管理している。

- `index.html` … フロントエンド（`doGet()`が`HtmlService.createTemplateFromFile('index')`で返す）
- `Code.gs` … バックエンド（Calendar操作・スプレッドシート連携などサーバー側ロジック）

Apps Scriptプロジェクトなので、変更を反映するには **Apps Scriptエディタ側に
このファイルの中身をコピペ**する必要がある（clasp等のデプロイ自動化は未設定）。
`/exec`の固定URLで運用している場合、保存しただけでは反映されず
「デプロイを管理→編集→バージョン:新規→デプロイ」が別途必要。

## データモデルの要点

- **予定＝患者の訪問**：1カレンダーイベント＝1患者訪問。タイトルが患者名（表記ゆれ対策の
  ヘルパーが `matchKey_` / `cleanTitle_` / `normName_`）。
- **担当者＝カレンダーの「ラベル」**（新しいGoogleカレンダーのカスタムラベル機能。
  `eventLabelId`）。色（旧colorId方式）は2026-08-08に廃止済みで、いまはラベルのみ。
  ラベル一覧取得・書き込みには拡張サービス（Advanced Calendar API）が必要
  （GASエディタの「サービス」から有効化）。
- **担当者の並び順**：シフト表スプレッドシート（`SHIFT_SPREADSHEET_ID`）の見出し行の順が
  基本。スクリプトプロパティ `COLUMN_ORDER` で手動上書き可能。
- **メモ**＝カレンダーイベントの `description`。フロント側は表示・編集のたびに
  `htmlToPlain()` でHTML→プレーンテキスト変換している。
- **次回訪問確認**：`confirmNextVisit` 系の関数が、タイトル冒頭に👌、末尾に
  【次回M/D】を付けて次回予定を確定させる仕組み（繰り返し予定はseriesId、
  単発は タイトル一致で次回を検索）。
- **患者マスタ**：`patientMasterRebuild()` が過去90日〜未来60日のカレンダーを
  スキャンし、患者ごとの住所・主担当・訪問頻度などをスプレッドシートにまとめる
  （手動実行のバッチ処理。ジオコーディングも別関数`geocodePending()`で行う）。
- **DRY_RUN**：`Code.gs`冒頭の`DRY_RUN`をtrueにすると、書き込み系の操作は
  実際にはカレンダーに反映されず`pendingChanges`に溜まり、ツールバーの
  「📤 反映」ボタンで一括反映するテストモードになる。通常運用はfalse。

## 仮担当機能（一時機能・要削除）

2026-09-17から2週間程度の期間限定で追加した機能。ある薬剤師が抜ける／変則対応期間中、
患者ごとに「仮の担当者」をメモ欄に明記する運用のために作った。**期間が終わったら
削除してよい**。該当箇所はコード中に `仮担当（一時機能` というコメントで
マークしてあるので、それを目印に以下をまとめて消せば元に戻る。

- `index.html`
  - ツールバーの `#karitanto-btn`（「🧑‍⚕️ 仮担当を確定する」ボタン）
  - `#karitanto-modal` のモーダルHTML一式
  - JS関数群：`pharmacistNameForColor_` `isUnassignedColor_` `openKaritantoModal`
    `renderKaritantoList_` `closeKaritantoModal` `confirmKaritanto`
  - Escapeキーハンドラ内の `closeKaritantoModal()` 呼び出し
- `Code.gs`
  - `KARITANTO_LOOKBACK_DAYS` 定数と `getKaritantoSuggestions()` 関数

### 何をする機能か

1. ツールバーの「仮担当を確定する」を押すと、表示中の日の患者一覧をモーダルで表示。
2. 各患者について、**過去半年（180日）でその患者を最も多く訪問している担当者**を
   サーバー側（`getKaritantoSuggestions`）で集計し、候補として提案する
   （担当ラベル別の訪問回数を`matchKey_`でタイトル一致集計）。
   半年間の実績がなければ、本日カレンダーに設定されている担当をフォールバックにする。
   提案できる担当者が誰もいない患者は一覧に出さない。
3. 患者ごとにチェックボックス（デフォルト全てON）で対象を選べる。不要な患者は外せる。
4. 「確定」を押すと、チェックした患者だけ、メモ欄の**先頭行**に
   `仮担当：〇〇`（〇〇は提案された担当者名）を追記する。既存のメモはその下に残る。
   同じ予定に再実行しても「仮担当：」行が重複しないよう、既存の行があれば
   置き換える（`/^仮担当：[^\n]*\n?/`を先に取り除いてから追記）。
   変更は**その日のイベント1件のみ**に適用（`updateEventFull`の`memoFuture=false`）。
   繰り返し予定の他の回には影響しない。
5. 実装はバックエンドの新規関数1つ（統計集計）以外、既存の`updateEventFull`を
   再利用しているだけなので、担当ラベルの書き込みロジックなどには一切手を
   入れていない。

### 既知の注意点

- `getKaritantoSuggestions`は過去180日分のカレンダーを毎回スキャンするので、
  予定数が多い場合はモーダルを開いてから一覧が出るまで数秒かかることがある。
  重ければ、`患者マスタ`側の集計を流用する／結果をキャッシュする、といった
  軽量化の余地がある（未実装）。
- 統計は「担当ラベルが付いている過去の予定」だけを数える。未登録（担当なし）の
  まま行われた過去の訪問はカウント対象外。

## 経緯（会話メモ）

- リポジトリ直下の「施設訪問記録」アプリについて「スケジュールアプリに接続できるか」
  という質問から会話が始まった → 現状は未連携（.ics書き出し／GAS Proxy経由の
  Googleカレンダー連携などが選択肢として出た、という議論のみで未実装）。
- その後、ユーザーが**既存の別プロジェクト**であるこの訪問スケジュールGASアプリの
  ソースをアップロードし、そちらに機能追加する流れになった。つまり「施設訪問記録」
  アプリとこの`schedule-app`は、会話の発端は同じでも**まだ実際には繋がっていない
  ２つの独立したアプリ**という点に注意（統合はまだ実現していない）。
